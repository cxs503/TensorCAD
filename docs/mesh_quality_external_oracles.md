# External-oracle differential — `GAP-CAD-D1-MESH-QUALITY-LIB`

*Anchor:* 网格质量指标库（aspect/skew/nonorth/jacobian/水密/流形/取向）
*Acceptance:* 与 meshmagick+Gmsh 指标对拍（≥3 网格、指标差异 < 1e-6 或差异解释）；可作 CI 门用
*Driver:* `tools/mesh_quality_external_diff.py` · *oracles:* `tools/mesh_quality_oracles/`
*Artifact:* `artifacts/mesh_quality_external_diff/oracle_diff.json`

The audit `docs/mesh-quality-lib-audit-m17404.md` §2 recorded the anchor's central item as
**NOT RUN**: no `gmsh`, no `vtk`, no `meshmagick` on this host, and the anchor's own
differential had never been executed against third-party code — only against a second
implementation written in the same tree. This document closes that item as far as the host
allows, and states exactly what remains unrun.

## 1. Why the oracles are code, not packages

| named oracle | status on this host | what was done instead |
|---|---|---|
| `meshmagick` | not on the package index (`pypi.org/pypi/meshmagick` → 404; not on the loong64 mirror); its `print_quality()` delegates to `vtk.vtkMeshQuality` | ran **Verdict**, the Sandia library that `vtkMeshQuality` calls (§3). Same arithmetic, no GPL/VTK runtime needed |
| `gmsh` (Python wheel) | no loong64 wheel on PyPI, no sdist, not on the loong64 index | obtained the **official 4.15.2 source** and a native loong64 `libgmsh`, wrote the harness `gmsh_oracle.cpp` against `gmsh::model::mesh::getElementQualities`; execution is blocked by the dependency closure, see §5 |

Neither oracle is vendored: both are third-party code of tens of MB, and both are located at
run time via `--verdict-oracle/--gmsh-oracle` or `TP_VERDICT_ORACLE/TP_GMSH_ORACLE`. When an
oracle is absent the driver reports `NOT_BUILT` — it never reports a pass it did not measure.

## 2. Corpus (6 meshes, 4 element kinds — the anchor asks for ≥3)

| mesh | kind | elements | how it is made |
|---|---|---:|---|
| `hex_unit` | hex | 8 | 2×2×2 structured grid on the unit cube |
| `hex_distorted` | hex | 12 | 3×2×2 grid with a deterministic sinusoidal node jitter (0.35 h) |
| `tet_cube6` | tet | 6 | Kuhn 6-tet split of the unit cube |
| `tet_sliver` | tet | 4 | hand-built flat/pinched tets (`z ≈ 1e-4…2e-3`), i.e. the degenerate corner |
| `tri_warped` | tri | 40 | 5×4 triangulation of a doubly-curved (sin·sin) patch |
| `quad_skewed` | quad | 12 | 4×3 quad patch with a 0.4 y-shear |

All are generated by `meshes()` in the driver — deterministic, no files, no external data — so
the differential is reproducible on any host that can build the oracles.

**14 of 18 compared pairs reach machine precision (≤ 2.4e-15), i.e. far inside the anchor's
1e-6.** The four that do not are not arithmetic errors; each is a *different definition*, and
each is now named instead of hidden:

| pair | worst element (ours / Verdict) | relation | classification |
|---|---|---|---|
| tet `scaled_jacobian` ↔ `tet_scaled_jacobian` | 0.408248290464 / 0.577350269190 | exactly **√2** on both meshes (and on `tet_sliver`: 0.00155585 / 0.00220031) | **normalisation**, explained: Verdict divides by the regular tetrahedron (ideal = 1), the library leaves the corner Jacobian un-normalised (regular tet = 1/√2). Constant, shape-independent |
| tri `aspect_ratio` ↔ `tri_aspect_ratio` | 1.25466309701 / 1.44876015361 | 2/√3 = 1.1547 at the worst element, **40/40 beyond 1e-6** | **definition defect in our label** (finding F5): the library's triangle `aspect_ratio` is R/(2r), which is Verdict's *`radius_ratio`*, not Verdict's `aspect_ratio` (= h_max·(a+b+c)/(2√3·\|ab\|)). Its docstring says "(Verdict; 1 = equilateral)", which is true only at the equilateral element |
| tet `min_dihedral` ↔ `tet_minimum_angle` | 45° / 60° on `tet_cube6`; 0.189° / 2.272° on `tet_sliver` | no constant relation | **different quantity**, explained: Verdict's `tet_minimum_angle` is a **face** angle (angle between two edges inside a face), the library's is a **dihedral** angle between faces |
| tet `skewness` ↔ `tet_equiangle_skew` | 0.6366 / 0.9998 on `tet_sliver` (agrees to 1.4e-16 on `tet_cube6`) | equal while the element is convex | **different angle basis**, explained: Verdict's tet equiangle skew is dihedral-based (TGrid), the library's is face-angle-based (the same basis as its `min/max_angle`); the two coincide until a face angle exceeds the dihedral spread |

### Finding F5 — triangle `aspect_ratio` is Verdict's `radius_ratio` (defect, reproducible)

```python
verdict_tri_aspect_ratio([[0,0,0],[1,0,0],[0.5,0.9,0]])  # 1.4… (Ver)
library aspect_ratio                                      # R/(2r) — Verdict's radius_ratio
```
Every one of the 40 warped triangles differs, worst by 15.5 %. Nothing downstream is
numerically wrong (the *gate* uses `min_sicn`, angles and a distilled aspect limit), but the
documented equivalence to VTK/meshmagick is wrong for this one metric. Remediation is a
labelling/threshold question, deliberately **not** changed here: renaming a public metric is an
API break and belongs in its own change with a deprecation path. Recorded so the next reader
does not repeat the audit's finding-F1 mistake (a dialect presented as "the same measure").

## 4. Gmsh differential — NOT RUN, with the harness complete and the blocker quantified

- Harness written and compiled: `tools/mesh_quality_oracles/gmsh_oracle.cpp` (native loong64
  `libgmsh.so.4.15.2` from the Debian pool, `gmsh::model::mesh::getElementQualities`), covering
  `minSICN`, `gamma`, `eta`, `volume`, `minEdge`, `maxEdge`, `innerRadius`, `outerRadius`.
  The mapping to the library is already encoded in `MAP["gmsh"]`, including the one pair
  expected to differ by construction (`min_sicn` vs `minSICN`: the library exposes Gmsh's unit
  as the separate metric `gmsh_icn`).
- **Why it did not execute:** Debian's `libgmsh.so.4.15.2` links, and therefore needs at run
  time, a closure that is not on this image — measured with
  `ldd libgmsh.so.4.15.2 | grep "not found"`: `libfltk{,_images,_gl}.so.1.3`, `libcgns.so.4.5`,
  `libmetis.so.5`, `libvoro++.so.1`, `libann.so.0`, `libalglib.so.4.7`, and ~20 OpenCASCADE
  `libTK*.so.7.9` (XCAF, DESTEP, DEIGES, Offset, Fillet, Mesh, BO, Prim, ShHealing, TopAlgo,
  …) plus their X11/fontconfig chain. Installing that closure is a multi-dozen-package change
  to the image, which is out of scope for a library task and cannot be done from the agent's
  worktree.
- `docs/mesh-quality-lib-audit-m17404.md` §6 answered "vs gmsh" with "cannot be answered".
  That answer is unchanged; what changed is that the *measurement apparatus* now exists
  (`--gmsh-oracle`), so the same command produces the numbers on a host with Gmsh, and the
  driver exits 2 under `--require-oracles` rather than pretending.

## 5. CI door

The anchor says "可作 CI 门用". `meshquality.cli`/`door.admit` provide the in-tree gate; the
*external* differential is a second, adversarial door:

```bash
python tools/mesh_quality_external_diff.py \
    --verdict-oracle "$TP_VERDICT_ORACLE" --gmsh-oracle "$TP_GMSH_ORACLE" --require-oracles
```

Exit codes: `0` every executed oracle agrees within 1e-6; `1` an executed oracle disagreed;
`2` a required oracle did not run. On an image without the oracles the honest outcome is `2`,
and `tests/test_mesh_quality_external_diff.py` keeps the protocol tested without them: it
re-checks the recorded artifact (every `AGREE` pair ≤ 1e-6, the four explained pairs present
with their documented relation) so a later edit that silently changes a metric fails the suite
even where no oracle can be built.

## 7. Limitations

- Verdict is meshmagick's *arithmetic* (`vtkMeshQuality` calls it), not meshmagick's *code*;
  meshmagick's own wrapper (mesh reading, unit conventions) is untested here.
- The corpus is synthetic and small (8–40 elements/mesh) but includes both ideal and
  degenerate elements; it does not cover the hull meshes used by the library's own benchmark,
  whose element connectivity could add orientation conventions the synthetic corpus lacks.
- Gmsh's half stays NOT RUN for the reason in §4; the library's `gamma`, `eta` and `gmsh_icn`
  were *transcribed* from Gmsh's source (which is on disk at
  `work/_ext/gmsh_src/src/geo/MTriangle.h`, `MTetrahedron.h`) but never diffed against a
  running Gmsh. Verdict agreeing with `gamma` to 7e-16 is corroboration of the triangulation,
  not of the Gmsh unit.
