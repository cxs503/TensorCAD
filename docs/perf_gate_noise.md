# 墙上时钟回归门的噪声口径：单发 vs best-of-N（GAP-CAD-D4-PERF-SCALE 续）

**锚点**: `GAP-CAD-D4-PERF-SCALE`（大几何性能基准 10⁶–10⁷ 三角级）
**口径手册**: `docs/perf_benchmark.md` §9 · **本文档完全由 `scripts/perf_gate_noise_repro.py` 从 JSON 工件渲染**，`python scripts/perf_gate_noise_repro.py --check` 在漂移时失败。

**测量环境**: loongarch64 · 3.11.6 · cpu=128 · load1/5/15 = 48.88/50.22/65.76

## 1. 为什么需要这一篇

v0.3 的结论是「闸门机制成立，但全绿只在安静机器上可复现」：共享机上连测三次，每次都出现 RED，**且 RED 落在不同行**。那些行的墙钟只有 0.03–0.2 s，RED 是计时噪声，不是回归。本版不改阈值（放宽 2× 会把真回归也放过去），而是改**测量与判据**三处：

1. **短测量重复取样**：基线 < 0.5 s 的键重复 3 次（累计受 3×上限约束），取 best-of-N；
2. **两侧同估计量**：基线也改成 `min` of 3 runs（v0.1–v0.3 是 `max` of 3）。只改测量侧会让估计量不对称——基线被负载噪声抬高多少，门就瞎多少；
3. **拒绝不可比**：`point_locate*` 的基线记录射线查询数，查询数不同时判 `not_run` 并给原因，不再拿两个不同工作量的时间相除。

**因果核对（射线查询数口径）**：`point_locate*` 的旧基线是在 500 条射线下录的，而文档给的 CI 命令 `--quick` 跑 1000 条。同一份代码在两种查询数下的实测比值：

| `point_locate_accel:81x21` | 0.0430 | 0.0917 | 2.13× |

比值落在 1.89–2.13×（线性于查询数，中位数 2.03×）：这就是那 7 个 `point_locate*` 键上「旧基线偏小」的来源，不是估计量造成的。两处原因必须分开记账：

* **估计量不对称**（`max` 基线 vs 单发测量）：影响全部 28 键，膨胀 1.1–2.1×；
* **工作量口径不一致**（500 vs 1000 射线）：只影响 `point_locate*` 8 键，让基线偏小约 2×，与上一条方向相反、部分抵消。

v0.4 的处置：基线改 `min` of N（与测量侧同估计量）、每键记录 `n_queries` 并在查询数不同时判 `not_run`（不是 pass），因此上面两类盲区都不再存在。

## 4. 注意点

- **只对短测量重复**（< 0.5 s）。10 s 档不是抖动问题，重复它会把闸门变成分钟级任务。
- **noise 是非 pass 非 RED 的第三态**：只有当同一份代码在同一次运行的重复之间跨越阈值、且离散度 ≥ 1.5× 时才成立；CLI 退出码 2。
- **基线仍与机器绑定**：跨架构拒比（`not_run`）。min-of-N 压低的是负载噪声，不是跨机器可移植性。
- **本轮实测没有触发 noise 第三态**（§2 全为 pass）：本机 load1≈/50 时两种协议的 3 次运行都全绿，所以本文不声称噪声分支被实测覆盖；它的行为由注入式单测 `tests/test_perf_gate_noise.py` 覆盖（同一份代码的重复取样跨越阈值时才成立）。
- 本文只覆盖 quick 阶梯（≤2.6×10⁴ 三角）。10⁶–10⁷ 带仍靠 `docs/perf_scale_reference.md` 的对比表守护，没有自动 RED 判定。

## 5. 误差判定（本节必答）

本文的「关键量」是闸门判定本身，不是物理量；对基准的比较如下：

| 量 | 基准 | 实测 | 偏差 | 是否 < 3% |
|---|---|---|---|---|
| 新基线下 pass 键占比 | 1.00（同代码同口径应全绿） | 1.000 | 0.000 | 是 |
| 旧基线对 2× 契约的偏离 | 1.00× | 2.08× （最高） | — | 否（结构性偏离，见 §3） |
| 查询数造成的基线偏差 | 1.00× | 中位数 2.03× | — | 否（见 §3 因果核对） |

逐键比值见 §2 的 JSON 工件（`ratios` 字段），无一处达到 2× 阈值；单发协议下的 RED/噪声行为亦如实列在表中，未做筛选。
