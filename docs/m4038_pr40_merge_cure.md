# PR #40 (re-opened) — union of `main` and `agent/m3169` under a second GZ route (m4038)

Repo `TensorCAD`. PR #40 (`agent/m3169`, "matured mission deliverables") was closed by the
owner on 2026-11-05 instead of merged; the task was re-opened as m4038 with the instruction
to *redevelop the feature on the current `main`*. This page records why the original PR
could not be merged as it stood, what the redevelopment changed, and the numbers that show
both routes work on the merged tree. `agent/m3169` is left in place as the archive.

## 1. State before the redevelopment

| ref | SHA | note |
|---|---|---|
| `origin/main` | `67e1d5c` | "Merge #45 (m3391) via merge-governor" |
| `origin/agent/m3169` (PR #40 head) | `fcf15ad` | last commit before the PR was closed |
| merge base | `df31744` | "Merge pull request #38"; the branch never saw `main` past it |

PR #40 was not a textual conflict. It was a **semantic duplicate**: between the merge base
and `main`, PR #45 landed `tensorcad/gz.py` — a complete large-angle righting-arm curve
(`heeled_hydrostatics`, `righting_arm_curve`, `wall_sided_righting_arm`,
`box_wall_sided_limit_deg`, `box_righting_arms_analytic`, `free_surface_correction`,
`with_freeboard`, 26 tests, `docs/gz.md`) — which answers the same question as the branch's
`tensorcad/righting_arm.py`. Merging it as delivered would have put two modules in the tree
claiming the same four public names with different signatures:

| name | `main` (`gz.py`) | PR #40 (`righting_arm.py`) |
|---|---|---|
| `righting_arm_curve` | `(mesh, kg, angles_deg=..., waterline_z=..., free_surface_i_x=...)` | `(mesh, *, kg, heels_deg=..., lcg=...)` |
| `RightingArmCurve` | `.gz`, `.kn`, `.angle_of_max_gz_deg`, `.range_of_stability_deg` | `.points`, `.gz_at()`, `.peak()`, `.vanishing_crossed()` |
| `wall_sided_righting_arm` | `(angle_deg, *, gm, bm)` | `(*, breadth, draft, kg, heel_deg)` |
| `wall_sided_validity_deg` | — (main has `box_wall_sided_limit_deg`) | `(*, breadth, draft, depth=None)` |

`tensorcad/__init__.py` could only bind one of each, so whichever module lost the binding
would have become unreachable from the package surface while its tests kept importing it
directly — a silent loss, not an import error.

## 2. Resolution: neither route is dropped, the overlap becomes the check

The two modules differ in *numerics*, not in physics, and that difference is worth being
able to run side by side:

| | `tensorcad.gz` (0.21.0, `main`) | `tensorcad.righting_arm` (0.22.0, PR #40 route) |
|---|---|---|
| heeled volume | divergence theorem on the rotated mesh, waterline driven by **Newton** on the projected wetted area (`dV/dc = A(c)`) | per-face clipped section integrated in the body frame, waterline by **bracket-and-bisect** on the monotone `V(h)` |
| unknowns | `KG`, optional free-surface `sum i_x` | `KG`, `lcg`, optional displacement override |
| curve products | `max_gz`, `angle_of_max_gz_deg`, `range_of_stability_deg`, free-surface correction | `peak()`, `vanishing_crossed()`, `area_under_curve()` (dynamical stability), `gz_at()` interpolation |
| refusals | open mesh, `|heel| >= 90`, non-finite, bad `kg` | same, plus displacement outside `(0, V_total)` |

So the cure keeps **both**, and gives the branch's route its own names at the package
surface (see `docs/righting_arm.md`, "Public surface"):

* `tensorcad.bisection_righting_arm_curve` ← `righting_arm.righting_arm_curve`
* `tensorcad.BisectionRightingArmCurve` ← `righting_arm.RightingArmCurve`
* `tensorcad.barge_wall_sided_righting_arm` ← `righting_arm.wall_sided_righting_arm`
* unchanged top-level bindings: `righting_arm`, `heeled_displacement`,
  `HeeledDisplacement`, `RightingArm`, `RightingArmError`, `wall_sided_validity_deg`,
  `DEFAULT_HEELS_DEG`

`tests/test_righting_arm.py::test_the_package_aliases_point_at_this_module` asserts both
directions (aliases → this module, plain names → `gz`), so a later edit cannot quietly
re-introduce the shadowing.

## 3. What the merged tree actually computes

Everything below is regenerated by `tools/verify_merge_m4038.py` into
`artifacts/m4038/merge_verification.json` and `merge_verification.png`; nothing is
transcribed by hand. All 7 of its claims pass.

### 3.1 The two routes on the same mesh, same `KG`, same displacement

| mesh | displacement (bisection / Newton) | `max |GZ_bisection − GZ_Newton|` | peak (both routes) |
|---|---|---|---|---|
| barge `L=10, B=2, T=0.8, fb=0.4 m`, `KG=0.55` | 16.000000 / 16.000000 m³ | **1.20e-13 m** | 0.1702 m @ 40° / 0.1702 m @ 40° |
| hull `41×13`, `z=-0.47 m`, `KG=0.55` | 3.552393 / 3.552393 m³ (5.8e-13 rel.) | **1.61e-13 m** | 0.13315 m @ 40° / 0.13315 m @ 40° |
| hull `81×25`, `z=-0.47 m`, `KG=0.55` | — | **6.89e-14 m** | — |
| sphere `R=1 m`, res 32, `KG=0.9` | — | **2.84e-16 m** | — |

Two independent waterline solvers agreeing to `1e-13 m` on a polyhedral hull is the
statement that neither route carries a modelling error the other lacks; what remains is
double-precision round-off.

### 3.2 Each route against its own reference

| check | result |
|---|---|
| barge `GZ` vs wall-sided closed form, inside the validity window (≤ 21.80°) | worst `1.21e-14 m` (example: `1.21e-14`) |
| the same formula **past** the deck edge (25–40°) | formula is up to `0.0955 m` out — the formula's limit, reported not smoothed |
| sphere vs `GM sin(phi)` = `0.1 sin(phi)` | worst `1.27e-04 m`, i.e. the mesh error at resolution 32, falling with refinement |
| hull small-angle slope vs `KB + I_T/∇ − KG` from `tensorcad.stability` (independent plane-section integration) | relative difference `6.3e-10 … 6.8e-10` over `21×9, 41×13, 81×25` |
| constant displacement along the curve | worst relative volume residual `2.1e-12` |

### 3.3 The negative control

The same barge with the `gz` curve's displacement target moved by 10 % moves `GZ(20°)` by
`-3.2e-03 m`, i.e. 3000× the round-off band. The comparison can fail; it is a check.

## 5. Limits, stated rather than smoothed away

* The two routes share the *mesh*, so a discretisation error in the hull cancels in the
  cross-check; §3.2 is what pins the discretisation (closed forms, refinement, waterplane
  moments), and the two must be read together.
* Neither route does damage, flooding, freeing ports, free trim, or classification
  criteria. `KG` is an input on both.
* The branch's curve refuses `|heel| > 90°`; `gz` refuses `|heel| >= 90°`. The one-degree
  gap is real (a `90°` heel is a degenerate waterplane) and is left as each module
  documented it rather than harmonised silently.
* `stability.waterplane_moments` still raises when the waterline lands exactly on a vertex
  ring of a `generate_hull` mesh (e.g. `nz=13`, `z=-0.5`); the volume route is unaffected,
  the example floats at `-0.47 m`, and this remains a reported finding of PR #40, not a fix.
