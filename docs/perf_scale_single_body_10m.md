# 单体 10⁶–10⁷ 三角面基准：细分几何源（GAP-CAD-D4-PERF-SCALE 续）

**锚点**: `GAP-CAD-D4-PERF-SCALE`（大几何性能基准 10⁶–10⁷ 三角级）
**被测**: `tensorcad.mesh_subdivision`（新）· `tensorcad.perf_subdiv`（新）· `tensorcad.spatial_index`
**前作**: `docs/perf_scale_10m.md` v2.0.0（网格/体素阶梯 + **多体 fleet** 10⁷ 带）
**本版 v3.0.0**: 10⁷ 单体档实测到件（作业 `cj3805`，节点 n330，rc=0）；新增「容量/集群判据」表
（`single10m-capacity`），把「什么规模需要集群」从推论变成实测速率×声明预算的乘法。
**工件（受版本控制，可复核）**: `benchmarks/perf_scale/artifacts/ladder_single_10m.json`
**渲染/漂移校验**: `tensorcad/perf_evidence.py` + `scripts/perf_scale_single_doc.py --check`

本篇只补一件事，也是前作 §6 第 1 条自己写下的结构欠账：

> "10⁷ 带靠 fleet 多体到达，单网格到不了……**导入式大网格仍未被实测**，这条限制是结构性的。"

本单把这个结构性限制拆掉——不靠多体装配凑数量，而是让**一个连通的闭合体**直接达到 10⁷ 三角面。

## 1. 案例介绍

**物理背景**：参数化船体（L=10 m，B=2 m，T=0.8 m，正弦型站位律）离散成三角形曲面后，
下游（BEM/FEM 面元、SDF 体素、求解器输入）关心的是"**一个** 10⁷ 三角面的连通曲面要多久加载、
能不能点定位、积分体积要多久、多少内存"。fleet 多体回答不了这个问题：它的 k 个副本互不相交、
装配是 O(N) 纯拷贝，点定位打到的永远是最近的那个体。

**几何来源（本单新增）**：`subdivide_mesh(mesh, levels)`——均匀 1→4 中点细分。
一个父三角形 `(a,b,c)` 分裂成四个，子三角形的绕向继承父绕向：

```
(a, m_ab, m_ca)   (m_ab, b, m_bc)   (m_ca, m_bc, c)   (m_ab, m_bc, m_ca)
```

中点按**无向索引对** `(min,max)` 去重，因此相邻面共享同一条边时拿到的是**同一个新顶点索引**——
焊接靠索引同一性，不靠浮点容差，也就没有任何"缝"。

**参数表**

| 项 | 值 |
|---|---|
| 父网格基座（本工件实测） | `401×129` → 205,598 三角；`1601×513` → 3,279,998 三角 |
| 细分级别 | 0,1,2,3（每级 ×4）：401×129 到 **13,158,272**；1601×513 到 **13,119,992**；1601×513 级 2（52,479,968）超 `max_triangles=1.6e7` 记 `not_run` |
| 子任务 | `load`（`generate_hull`）、`subdivide`（单级细分墙钟）、`volume`（散度定理）、`point_locate_accel`（`TriangleGrid` 均匀网格+DDA，**2000** 条射线） |
| 10⁷ 档 | **已实测**：作业 `cj3805`（n330，rc=0，墙钟 771.7 s），`summary.single_body_10m_reached = true` |
| 解析基准 | `hull.analytic_volume(10, 2, 0.8)`（闭式解，与采样无关） |
| 计算资源 | 经 `run_compute` 递交集群（loongarch64，128 核，作业时 loadavg 47）；本机只跑 ≤2 min 测试 |
| 复现命令 | `python scripts/perf_scale_single10m.py --bases 401:129,1601:513 --levels 0,1,2,3 --queries 2000 --max-triangles 16000000 --output benchmarks/perf_scale/artifacts/ladder_single_10m.json` |

**为什么"细分"不是作弊**：细分不改变几何形状以外的任何测量口径——
它把同一个**离散**多面体加密，而每个平面父三角形被四个子三角形**精确铺满**。于是：

* 体积（散度定理）与表面积在细分前后**必须逐位一致**（差异只有浮点累加序）；
* 拓扑不变量按 `V' = V + E`、`F' = 4F`、`E' = 2E + 3F` 精确推进，`V'-E'+F' = 2` 不变；
* 因此 10⁶ 档与 10⁷ 档是**同一个体**的两个离散密度——这正是"同一物体在不同三角数下要多贵"
  这个问题需要的对照条件，而 fleet 的两档是**不同的体**。

## 2. 怎么做的

1. **细分算子**（`tensorcad/mesh_subdivision.py`，stdlib-only，零依赖）：单趟遍历父面，
   建 `{(min,max): 新顶点索引}` 表 → 追加中点 → 展开四个子面；多级迭代复用同一实现。
   成本 O(F)，内存 O(F+E)。
2. **驱动器**（`tensorcad/perf_subdiv.py`）：每个基座生成一次父网格（`load` 计时），
   沿级别阶梯逐级细分，每级测 `subdivide`（单级墙钟）、`volume`、`point_locate_accel`
   （索引构建时间单列 `build_seconds`），并逐级记录不变量（水密/边流形/Euler/体积漂移/面积漂移）。
   超过 `max_triangles` 的档**记录 `not_run` 与预期三角数**，不是静默跳过也不是硬跑 OOM。
3. **CLI**（`scripts/perf_scale_single10m.py`）：产出
   `benchmarks/perf_scale/artifacts/ladder_single_10m.json`；日志里同时打印人读表。
4. **证据绑定**：`tensorcad/perf_evidence.py` 三个新渲染器（`single10m-table` /
   `single10m-invariants` / `single10m-exponents`）把工件渲染成下方表格；
   `scripts/perf_scale_single_doc.py --check` 在文档与工件不一致时失败，
   `tests/test_perf_subdiv.py::test_committed_document_matches_committed_artifact` 把这条绑定进 CI。
5. **方法学对照**：同一台机器、同一作业内的跨档比值才可比；跨作业只比数量级。

## 5. 注意点 / 局限（诚实记录）

0. **10⁷ 档已到件（v2 的头号欠账已消）**：作业 `cj3805`（n330，rc=0，墙钟 771.7 s）产出
   `ladder_single_10m.json`，实测最高 13,158,272 三角，`single_body_10m_reached = true`。
   到件链路本身的教训值得记：前两次（`cj2967`/`cj2976`）不是算错，而是**产物没随日志回来**——节点把结果
   写进工作树里一个未跟踪路径，取回只带提交时已跟踪的文件，几分钟的测量被静默丢弃。现在
   `tensorcad/perf_scale_artifact` 同时写文件 **并**在日志里打 gzip/base64 分块（`PERF10M_JSON_BEGIN/END`），
   任一通道活着即可还原，且截断会**报错而不是返回半份结果**；本版工件即由此通道取回后落盘。
1. **peak RSS 只有一套口径**：`peak_rss_mb` 是进程高水位，1601×513 的 `load`（186.7 s 生成 3.28M 三角）
   把高水位抬到 6.8 GB，同进程后续档的 peak 都被它带高；「这一档要多少 RAM」请读 `rss_mb`/`mesh_mb`/
   索引 MiB，不要读 peak。
2. **细分不改形状**：10⁷ 档的形状等于它 10⁶ 父网格的分片线性形状。因此本表回答"同一离散曲面
   加密到 10⁷ 三角有多贵"，**不**回答"10⁷ 三角的 CAD 曲面比 10⁶ 的更准吗"。后者的误差由父网格
   离散度决定，表中 `vs 解析` 一列逐级常量（不随细分改善），这正是判据的证明。
3. **仍不是文件导入路径**：本单消除了"单连通体"这一层，但"从 OBJ/STEP 读入 10⁷ 三角"仍含解析、
   分块与容差焊接的开销，未被本单覆盖。剩余欠账只在这一段（见 §6 建议）。
4. **射线起点在原点**（与既有框架一致）：船体尾端在原点，越过半数的方向天然不命中；命中计数
   记录在 `note` 里，可核对查询是否真的打到了网格，而不是在空腔里空转。
5. **peak 与活 RSS 的区别**：`peak_rss_mb` 是进程高水位（`ru_maxrss`），不能逐档复位；"这一档要多少 RAM"
   读 `mesh_mb` + `index MiB` + 活 RSS 三列。
6. **`max_triangles=1.6e7`** 是共享节点的内存护栏（13.1e6 档的网格 + 索引已在数 GB 级），
   更大的档（如 5.2e7）需要先估内存再放开，否则会以 OOM 而不是以数据结束。

## 6. 误差判定（关键量 vs 基准，逐项显式回答）

| 关键量 | 基准 | 判定 | 是否 <3% |
|---|---|---|---|
| 体积（**10⁷ 档**散度定理） vs 父网格同一量 | 细分精确铺满 ⇒ 逐位一致 | 13,158,272 档 +4.61e-11 %（`summary.max_volume_rel_drift_vs_base = 4.61e-13`） | ✅ 是 |
| 表面积（同） | 同上 | 见 §3.1 `面积漂移` 列 | ✅ 是 |

| 拓扑（水密/边流形/Euler） | 全边二面、χ=2 | 见 §3.1 三列，全部 ✅ | ✅ 是（离散判据，非百分比） |

**是否 <3%**：细分保真（本单新增能力）**是**；体积对解析解的误差继承自父网格离散度，
`1601×513` 父网格下已在亚百分比量级——具体数字由 §3.1 表程序化给出，不在正文手抄。
本单**没有**声称性能绝对值可跨机复现（见 §5.4）。

## 7. 容量与集群判据（本版新增，程序化渲染）

本节回应验收第 3 条「记录在什么规模上需要集群」。做法不给经验阈值，而是把**实测速率**乘上声明的预算：
时间上限 = 最大实测档速率 × 预算；内存上限 = 声明的 RAM 预算 ÷ 实测 B/tri。
两个上限并列，因为它们在**不同子任务**上先触顶——读者可换掉预算自己重算，不必相信任何拟合参数。

索引 79.5–79.9 B/tri（4 档 ≥10⁶ 一致，与来源无关）；细分档在索引前 202 B/tri、建索引后 284 B/tri（差额即索引本身）；生成档 944 B/tri——多出的是生成器参数网格常驻，不是三角面本身。
<!-- perf-evidence:single10m-capacity end -->

**判读（数字均出自上表，可在工件里复核）**：

1. **`volume` / `subdivide` 的时间上限远高于内存上限**（10⁸–10⁹ 三角 vs 8.5×10⁷）：二者都是单遍循环
   （NumPy 散度定理、索引同一性展开），10⁷ 只要 5.9 s / 17.5 s，**时间不是墙**。
2. **`load`（参数化生成）先被时间卡住**：17,564 tri/s 是单线程 Python 生成器，10⁷ 就等于 570 s 墙钟，
   60 s 预算只到 1.05×10⁶。**加核不救它**——所以「要集群」的真原因不是算力不足而是**并行度**：
   单进程单线程的生成路径在 10⁶ 带以上已是分钟级。
3. **`point_locate_accel` 的墙是一次性建索引**：10⁷ 档查询本身 1.29e3 query/s（60 s 可打 7.7 万条射线），
   但建索引 98 s、索引 997 MiB。索引成本 **79.5 B/tri**（4 档 ≥10⁶ 一致，与几何来源无关）。
4. **内存口径**：细分档 10⁷ 活 RSS ≈284 B/tri（其中 ~80 B/tri 是索引），16 GiB 预算下上限 ~6×10⁷；
   生成档另加参数网格常驻（944 B/tri），上限降到 ~1.8×10⁷。**10⁸ 三角级（≈28 GB 活 RSS + ≈8 GB 索引）
   已超出本次实测口径，必须走集群/分块——这就是本表给出的量化分界**。

**与前作口径的关系**：前作 §10.4 用同样的「速率×预算」乘法在**多体 fleet** 上给等价规模；本节是同一口径在
**单体**上的复核，并按子任务拆开——因为集群判据对 `load`、`volume`、`point_locate` 是三个不同的数字。
